Harbour Design System

A small, accessible design system for a fictional insurance company: design tokens, seven reusable components, usage guidelines and naming conventions. Every colour pair is checked against WCAG 2.2 AA, and every page is tested automatically with axe-core.

Design principles

Clear before clever

Plain words, one primary action per screen, and labels that say what happens next.

Accessible by default

Contrast, focus, keyboard use and screen reader names are built into each component, so teams do not have to remember them.

Tokens, not overrides

Teams change the look through tokens. Behaviour stays in the component, so it stays consistent everywhere.

Design tokens

Tokens are named design decisions. Source of truth: tokens/tokens.json, compiled to CSS variables by npm run tokens.

Spacing, radius and type

Spacing uses a 4px base: --ds-space-1 (4px) to --ds-space-7 (48px). Radius: sm 4px, md 8px, lg 12px, pill. Type sizes: 0.875rem, 1rem, 1.25rem, 1.75rem. Minimum touch target: --ds-target-min = 44px.

Components

Button

Use a button for an action and a link for navigation. One primary button per screen.

Do

Start labels with a verb: “Submit claim”, “Upload receipt”.

Don't

Use vague labels like “Click here” or “OK” that make no sense out of context.

Accessibility: disabled buttons use aria-disabled instead of disabled, so keyboard and screen reader users can still find them. The loading state uses aria-busy, and the spinner stops when the user prefers reduced motion.

Text field

8 digits, on your policy card

Accessibility: every input has a visible <label>. Hints and errors are linked with aria-describedby, errors set aria-invalid, and error text starts with “Error:” so it does not rely on colour alone.

Checkbox and radio group

How should we contact you?

Accessibility: related options are grouped in a <fieldset> with a <legend>, and each row is a 44px target.

Switch

Use a switch for a setting that takes effect immediately; use a checkbox inside forms that are submitted later. Accessibility: role="switch" with aria-checked; Space and Enter toggle it.

Accessibility: each alert has a written title, not only a colour or icon. Errors use role="alert" so they are announced immediately.

Tabs

Claim submitted on 12 November. Status: in review.
2 receipts uploaded.
No changes yet.

Keyboard: Tab moves into the tab list, Left/Right arrows switch tabs, Home/End jump to the first or last tab.

Dialog

Cancel this claim?

You will lose the details you entered. This cannot be undone.

Accessibility: focus moves into the dialog, Escape closes it, and focus returns to the button that opened it. The safe choice comes first.

Accessibility checklist (WCAG 2.2 AA and AODA)

Ontario's AODA requires WCAG 2.0 AA for public websites of large organizations. This system targets WCAG 2.2 AA.

WCAG success criteria and how the system meets them
WCAG criterionHow the system meets it
1.4.3 Contrast (minimum)All text pairs are at least 4.5:1, checked by an automated test.
1.4.11 Non-text contrastBorders and focus ring are at least 3:1.
1.4.1 Use of colourErrors and alerts have text labels, not just colour.
2.1.1 KeyboardEvery component works with a keyboard; tabs and dialogs follow WAI-ARIA patterns.
2.4.7 Focus visible3px focus outline on every interactive element.
2.5.8 Target size (minimum)Targets are 44px, above the 24px minimum.
3.3.1 Error identificationErrors are described in text and listed in an error summary.
3.3.2 Labels or instructionsVisible labels and hints on every field.
4.1.2 Name, role, valueNative elements first; ARIA roles and states where needed.

Automated checks catch only some problems, so each component should also be checked by hand with the keyboard and a screen reader such as NVDA (see the test plan in the case study).
